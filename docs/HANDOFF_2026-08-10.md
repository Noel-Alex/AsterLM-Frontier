## 1. User objective

Build the strongest language model that can be researched and substantially trained on the user's
12 GiB RTX 4080 Laptop GPU, with optional bounded cloud bursts. Optimize quality, training speed,
inference speed, memory and research value together. Energy is recorded for statistics and
diagnostics only; it is not a training or architecture decision criterion. The project is also an educational
instrument: checkpoints, data lineage, capability growth, failures, metrics and decisions must remain
inspectable long after a run finishes.

The user is willing to run careful research, port or write kernels when evidence requires it, and use
authorized cloud credits. Do not confuse that ambition with permission to make unsupported claims,
farm promotional accounts, start unbounded paid jobs, or replace measured engineering with fashionable
architecture names.

The target of 100B training tokens is a research budget hypothesis. It is not evidence of grokking,
frontier quality or compute optimality. Scaling must be earned through smaller controlled experiments.

## 2. Non-negotiable operating rules

1. Preserve evidence. Raw run artifacts, manifests, traces, checkpoint metadata and failure rows are
   research data even when the model is bad.
2. Separate archived evidence from new evidence. Never rewrite old runtime or result claims after an
   environment changes.
3. Use matched controls. Dense versus MoE, KDA versus MLA, precision, optimizer and kernel comparisons
   must vary one meaningful factor at a time.
4. Record code/config hashes, provider/profile aliases, data cursors and runtime manifests for every
   consequential run.
5. Never expose provider tokens through Studio, logs, Git or handoff documents.
6. Never start a remote paid job without an explicit timeout, cost ceiling, checkpoint destination and
   user cost confirmation.
7. Do not call a configured context length “validated.” Train it and evaluate retrieval/quality.
8. Do not call a short architecture screen a final quality verdict.
9. Prefer compatible, maintained kernels before custom CUDA/Triton work. Write or port a kernel only
   after an operator trace proves the remaining bottleneck and the license permits it.
10. Keep the old cream/broadsheet Studio theme. The user explicitly rejected the dark redesign; visual
    redesign is deferred while functionality is built.

## 7. Attention and kernel reality

Read `docs/research/KERNEL_COMPATIBILITY_2026-08-10.md`.

- The current training KDA path is FLA 0.5.2 Triton chunk KDA with safe gate enabled and lower bound
  `-5`.
- Official Moonshot FlashKDA v1 is inference-only, requires K=V=128 and publishes builds for SM90a,
  SM100a, SM103a and SM120a. The laptop is Ada SM89 and the vNext2 head dimension is 64.
- Official DeepSeek FlashMLA targets SM90/SM100, not Ada SM89.
- Internal math being portable to older MMA instructions is not the same as a published supported
  build. Do not bypass architecture guards and call the result supported.
- The absorbed MLA A/B/B/A scout was about 4.7% faster than reconstructed MLA in the small systems
  test and remains the Ada MLA baseline.
- Long-context architecture quality is unresolved. KDA, Gated DeltaNet-2, gated NoPE MLA and sparse
  attention must be evaluated on retrieval/interference tasks, not only 2K cross entropy.

Before custom kernel work, profile and compare:

1. existing Transformer Engine grouped GEMM;
2. reference experts;
3. fewer/wider expert shapes;
4. microbatch/sequence rows per expert;
5. `torch.compile` compatibility and graph breaks;
6. dispatch/sort/index-add fusion;
7. optimizer/gradient norm tensor fragmentation.
