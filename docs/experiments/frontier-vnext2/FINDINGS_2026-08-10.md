## What was actually run

- 49 trials: 43 completed, 2 CUDA OOM, 4 errors.
- Total measured trial time: 18,616.34 seconds (5.171 GPU-hours).
- Proxy corpus: 24,006,881 train tokens and 2,402,806 validation tokens, vocabulary 32,768.
- GPU: NVIDIA RTX 4080 Laptop, 12,282 MiB reported VRAM, Ada compute capability 8.9.
- Recorded runtime: PyTorch 2.13.0+cu132, Transformer Engine 2.17.0, FLA 0.5.1,
  Triton 3.7.1, TorchAO 0.17.0 and APOLLO 1.0.

This proxy is controlled architecture evidence, not the final pretraining corpus. The architecture
screens used only about 4.19M tokens at sequence length 2,048; they cannot support a final quality
verdict or a long-context claim.

## MoE utilization result

| Architecture screen | Median tok/s | Median GPU util | Median power | Median SM clock |
|---|---:|---:|---:|---:|
| Dense, all MLA | 15,928.65 | 84% | 113.70 W | 2,340 MHz |
| Grouped MoE, KDA3 | 9,552.22 | 63% | 94.92 W | 2,400 MHz |
| Latent MoE, KDA3 | 8,064.74 | 59% | 84.05 W | 2,415 MHz |
| "Stable" latent MoE, KDA3 | 8,012.89 | 61% | 84.98 W | 2,415 MHz |

The low MoE utilization is real and abnormal for the intended result, but the evidence points to an
underfed GPU rather than thermal throttling: utilization and power fall while clocks remain similar.
At sequence length 2,048, micro-batch 1 and gradient accumulation 16, an 8-expert/top-2 layer has
roughly 512 routed token rows per expert per micro-batch; 16 experts/top-2 has roughly 256. Gradient
accumulation does not combine those rows into larger expert GEMMs. Kernel launch, routing, sorting,
padding, Python/host synchronization and many small GEMMs can therefore dominate.

The first code-level fixes following this audit are deliberately evidence-directed:

- removed repeated authoritative-weight binding in the Transformer Engine grouped expert path;
- replaced duplicate routing sort/index construction with one sort and derived token indices;
- replaced dense one-hot router-load accounting with `bincount`;
- removed unconditional device-to-host scalar extraction in latent-MoE load tracking;
- stopped collecting Python router summaries on non-logging steps;
- kept loss accumulation on device, eliminating up to five host synchronizations per micro-batch;
- removed the remaining per-microbatch finite-loss host gate; the finite-gradient gate still runs
  once before every optimizer step, so invalid parameters cannot be committed;
- combined GPU telemetry fields into one `nvidia-smi` sampling query and fixed overwritten trial names.

These are not yet performance claims. They must pass the matched benchmark protocol below.

### 2026-08-10 matched follow-up

The corrected implementation was then measured with continuous 0.5-second GPU sampling, five warm-up
updates, 20 measured optimizer updates, three repetitions, sequence length 2,048, micro-batch 1 and
gradient accumulation 16. Results are in:

- `runs/frontier-vnext2/moe-utilization-dense-kda3-20260810/matrix.json`
- `runs/frontier-vnext2/operator-profiles-20260810/`

| Variant | Median tok/s | Median GPU util | Median power | Tok/J | Peak allocated |
|---|---:|---:|---:|---:|---:|
| Dense all-MLA | 12,086.29 | 66.0% | 98.22 W | 123.06 | 3.55 GiB |
| Dense KDA3 | 10,714.43 | 59.5% | 91.08 W | 113.06 | 3.77 GiB |
| Grouped MoE KDA3 | 5,908.95 | 43.0% | 75.13 W | 78.97 | 5.21 GiB |
| Latent MoE KDA3 | 5,010.62 | 39.0% | 68.00 W | 73.69 | 5.37 GiB |

Relative to matched dense KDA3, grouped MoE is 44.85% slower, 30.15% worse in tokens/joule,
16.5 utilization points lower and 38.22% higher in peak allocated VRAM. Latent MoE is 53.23%
slower, 34.83% worse in tokens/joule, 20.5 utilization points lower and 42.31% higher in peak VRAM.
All three repetitions completed, and the result is directionally consistent with the archived screen.

This matrix is diagnostic rather than promotion-grade: the Codex/ChatGPT desktop UI was using roughly
17% SM at the initial baseline and the run used an explicitly raised 25% idle ceiling. Light interactive
CPU work also occurred during the three-way matrix. Continuous sampling and balanced trial order make
the comparison useful for debugging, but the final publishable table must be rerun detached with the UI
closed and no concurrent work.

One-update operator profiles further localize the deficit:

| Variant | Forward + backward | Optimizer + clipping | `aten::mm` events |
|---|---:|---:|---:|
| Dense KDA3 | 268.56 ms | 151.06 ms | 778 |
| Grouped MoE KDA3 | 415.45 ms | 333.08 ms | 1,196 |
| Latent MoE KDA3 | 489.97 ms | 524.10 ms | 1,592 |

Grouped MoE forward/backward is 54.7% slower than dense KDA3 in the trace; latent MoE is 82.4%
slower. Optimizer/clipping is 2.2x dense for grouped and 3.5x for latent. The traces show hundreds of
small 64x64 or 32x64 expert GEMM tiles plus thousands of elementwise, division, norm and index-add
operations. Balanced router telemetry and similar SM clocks rule out expert collapse and thermal
throttling as the primary explanation. The immediate targets are therefore:

1. increase routed rows per expert by testing fewer experts, top-1, larger micro-batches and longer
   sequences one factor at a time;
2. reduce expert tensor fragmentation and verify Transformer Engine grouped-GEMM fusion boundaries;
3. isolate dispatch/sort/index-add and gradient-norm/optimizer launch overhead;
4. compare grouped and reference expert implementations at matched active parameters;
5. consider an Ada-specific fused expert path only if existing grouped GEMM backends remain limiting.

KDA accounts for only part of the original dense-versus-MoE gap: dense KDA3 is 11.35% slower than
dense all-MLA in this short-context diagnostic, whereas grouped MoE remains 44.85% slower than dense
KDA3. Replacing attention cannot fix the expert-path utilization problem.

### Work-granularity causal screens

One-repetition rejection screens then varied model shape and workload independently. They retain the
same diagnostic/interactively loaded classification and require repeated confirmation.

| Screen | Tok/s | GPU util | Power | Tok/J | Peak allocated |
|---|---:|---:|---:|---:|---:|
| E8/top-2/H704, batch 1, seq 2K | 6,238.57 | 44.0% | 76.44 W | 81.62 | 5.21 GiB |
| E4/top-2/H704, batch 1, seq 2K | 6,534.55 | 45.0% | 76.32 W | 85.62 | 4.52 GiB |
| E4/top-1/H1408, batch 1, seq 2K | 6,722.50 | 48.0% | 82.28 W | 81.70 | 5.39 GiB |
| E8/top-2/H704, **batch 2**, seq 2K | **11,151.76** | **66.0%** | 105.04 W | **106.17** | 8.11 GiB |
| E8/top-2/H704, batch 1, **seq 4K** | **10,567.85** | **64.5%** | 101.07 W | **104.56** | 8.12 GiB |

Fewer/wider experts help modestly, but doubling tokens in the microbatch is decisive: batch 2 is
78.76% faster than the same-screen batch-1 baseline and uses the same 32,768 tokens per optimizer
update after accumulation changes from 16 to 8. Sequence 4K independently produces a 69.39% gain.
Both nearly double routed rows per expert from about 512 to 1,024. This causally supports GPU
underfeeding as a major issue.

The matched three-repetition confirmation at batch 2/accumulation 8 completed successfully:

| Variant | Median tok/s | Median GPU util | Median power | Median tok/J | Peak allocated |
|---|---:|---:|---:|---:|---:|
| Dense KDA3 | **18,071.32** | **95.5%** | 117.48 W | **155.01** | 6.17 GiB |
| Grouped MoE KDA3 | **11,331.62** | **66.0%** | 105.06 W | **106.29** | 8.12 GiB |

The higher-workload MoE result is repeatable, but it is not dense parity: grouped MoE remains 37.30%
slower, 31.43% worse in tokens/joule, 29.5 utilization points lower, and 31.57% higher in peak
allocated memory. Dense KDA also benefits strongly from batch 2, so underfeeding explains much of the
absolute utilization improvement but not the remaining expert-path deficit. The next causal work is a
reference-versus-grouped comparison at batch 2, followed by isolation of the separately executed
shared expert, dispatch/index-add, and optimizer/gradient-norm tensor fragmentation. Quality,
optimizer behavior and numerical stability must still be checked at equal tokens before promotion.

## Attention conclusions (and non-conclusions)

- `dense-all-mla` is a control baseline, not the final architecture decision.
- The absorbed MLA A/B/B/A scout was about 4.7% faster than reconstructed MLA in that small systems
  test. It should remain the Ada baseline.
- KDA means Kimi Delta Attention. It is not DeepSeek Sparse Attention.
- DeepSeek's official FlashMLA targets SM90/SM100, so it cannot run on this Ada SM89 laptop.
- Moonshot's FlashKDA design uses SM80 MMA internally, but the published v1 build supports SM90a+
  and inference only. It also requires K=V=128, while this screen uses head dimension 64. It is not
  an executable Ada candidate without a non-trivial port; current training uses FLA's Triton KDA.
- The "stable latent MoE" screen only changed `latent_moe_post_norm=true`. It was not a faithful Kimi
  K3 Stable LatentMoE implementation and therefore cannot reject that published architecture.

## Power interruption annotation

`dense-all-mla-lr3e-4` completed its entire 8,388,608-token budget and wrote its final checkpoint.
The brief unplug is visible in two roughly five-second telemetry samples (about 55 W at 1,185 MHz,
then about 54 W at 870 MHz) and two throughput dips at steps 224 and 228. Throughput immediately
returned from 11.6-12.2K tok/s to about 16K tok/s. The quality result and checkpoint remain valid;
median throughput is the robust performance statistic. Do not spend time rerunning it solely because
of the unplug; retain the annotation in comparisons.

## Performance gate for the next campaign

No architecture or kernel earns promotion from a single fastest number. Each candidate must use:

1. identical seed, data ordering, optimizer, schedule, tokens and validation set;
2. warm-up excluded from timing, at least 20 measured optimizer steps, and three repetitions where
   run cost permits;
3. tokens/s, update latency distribution, peak allocated/reserved VRAM, GPU utilization, power,
   tokens/joule, achieved TFLOP/s estimate, router balance/drop/overflow and compile time;
4. forward/backward/optimizer profiler traces for dense and MoE at matched active parameters;
5. validation loss/perplexity parity and deterministic checkpoint/resume verification;
6. separate training and inference Pareto fronts—prefill, decode, latency, throughput, memory and
   long-context retrieval quality are not interchangeable;
7. failure rows retained with completion fraction and failure class.

The immediate MoE matrix should vary micro-batch size, sequence length, experts/top-k, capacity,
grouped vs reference experts, and compile/precision backend one factor at a time. The primary question
is whether expert GEMM occupancy rises with routed rows per expert. Only after the trace identifies a
remaining hotspot should a custom Triton/CUDA kernel be considered. Existing PyTorch grouped GEMM,
Transformer Engine, FLA, FlashAttention/SDPA and compatible published kernels are benchmarked first.

## Research interpretation

The 100B-token goal is a training-budget target, not a guarantee of grokking. Grokking requires a
defined task/capability, held-out generalization curve and a reproducible transition; simply consuming
100B tokens is not sufficient. Checkpoints and evaluations must therefore be dense enough to study
capability growth, scaling behavior, data repetition, memorization and any delayed generalization
without retroactively inventing a claim.
